## 2. 기술적으로 설명할 수 있는 내용

- 사용한 핵심 기술 및 선택 이유: PostgreSQL을 사용해 사용자, 문장, 연습 기록, 개별 오류를 관계형 테이블로 관리했다. 테이블 간에는 UUID 외래 키를 사용해 기록의 연결 관계를 유지했다. Python에서는 `psycopg`로 DB에 접근하고, SQL을 기능별 파일로 분리해 쿼리의 목적과 수정 위치를 확인하기 쉽게 했다.
- 가장 어려웠던 문제와 원인: 팀원별 브랜치의 코드가 서로 달라 화면에서 호출하는 DB 함수 또는 SQL 파일이 통합본에 없는 문제가 있었다. `db.py`, SQL 파일, 화면 코드가 함께 반영되어야 정상 작동하는 구조가 원인이었다.
- 직접 구현한 해결 과정: 화면에 필요한 조회·저장 함수를 `src/db.py`에 연결하고 SQL 파일을 추가했다. 연습 결과 저장 시에는 먼저 `practice_runs`의 ID를 받은 뒤 해당 ID로 개별 오류를 `error_items`에 연결하도록 구성했다. 팀원들과 필요한 DB 함수 및 반환값을 확인하며 통합 작업을 지원했다.
- STT/TTS 파이프라인 이해 내용: TTS는 기준 문장을 음성으로 생성해 사용자에게 들려준다. 사용자가 녹음하거나 업로드한 음성은 STT를 거쳐 텍스트로 변환되고, 평가 함수가 기준 문장과 비교해 WER·CER·대치·삭제·삽입·점수를 계산한다. 내가 담당한 DB 부분은 계산된 결과를 저장하고 학습 이력과 관리자 통계에서 다시 조회할 수 있도록 연결하는 것이다.

## 3. 협업·코드 리뷰

- 본인이 리뷰한 코드: `app_practice.py`에서 평가 결과가 `save_practice_run()`과 `save_error_items()`로 전달되는 흐름을 확인했다. `app_home.py`의 관리자 로그인과 세션 상태가 DB 사용자 정보와 연결되는 부분, `app_manager.py`가 요구하는 통계 항목과 DB 조회 함수의 반환값도 팀원들과 대조했다.
- 다른 팀원으로부터 받은 피드백: 관리자 화면에 필요한 등록 사용자 수, 사용자별 연습 횟수, 카테고리·난이도·문장별 집계 항목을 UI 담당자와 논의했다. 등록일과 연습 횟수의 정렬 기준에 관한 피드백을 받았고, 개별 오류를 CER의 글자 단위 계산과 맞춰 저장해야 한다는 의견을 반영했다.
- 역할 분담의 적절성: DB 구조, 저장·조회 함수, 관리자 통계 SQL을 맡은 분담은 명확했다. 다만 DB 함수의 이름과 반환값이 UI·평가 코드에 직접 영향을 주는데, 변경 사항과 통합 기준이 늦게 공유되어 기능 연결을 확인하는 작업이 추가로 필요했다.

## 5. 다음 프로젝트 개선점
이번 프로젝트에서는 화면과 DB를 각각 수정하다 보니 통합본에서 필요한 함수나 SQL 파일이 빠진 것을 뒤늦게 발견했다. 다음에는 작업을 시작하기 전에 화면에 필요한 데이터와 DB 함수의 입력·반환값을 팀원들과 정리하겠다. 변경 사항을 합칠 때마다 로그인부터 평가 결과 저장, 학습 이력 조회까지 직접 확인하고 테스트 결과를 기록하겠다. 연습 기록과 개별 오류는 함께 저장되도록 개선해 한쪽 데이터만 남는 문제를 방지하겠다.
sql문 기준으로 사용방법만 설명해서 팀원들이 어려웠다 데이터 저장 구조 부터 설명을 했어야 했다.
특히 ui가 db를 바로 import 해야하는 게 아니라 중간에 나누는 logic파일을 하나 뒀어야 했다.
현재 logic 과 ui가 합쳐진 상태이다.
